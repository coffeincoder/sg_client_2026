# Правила работы с git — коммиты и пуши

Короткий чек-лист, чтобы безопасно менять код на ~100 клиентов в поле.
Применяется к **обоим** проектам: `sg_client_2026` и `sg_orange_2026-`.
Про совместимость протокола — отдельный файл `COMPATIBILITY.md`.

---

## 🔴 Жёсткие правила (нарушать нельзя)

1. **Не коммитить и не пушить прямо в `main` и `dev`.**
   Любое изменение — через свою ветку: `git switch -c fix/<название>` (или `feat/…`, `refactor/…`, `docs/…`).
2. **Не пушить, не посмотрев весь diff.** Сначала `git diff` / вкладка diff на GitHub — глазами по всем изменениям, потом push.
3. **Не удалять и не переписывать ветки `baseline-2026-06`.** Это точка возврата к заведомо рабочему состоянию (`git checkout baseline-2026-06`).
4. **Перед merge — открыть `COMPATIBILITY.md`.** Не трогаю ли ключи протокола/MQTT/JSON? Если да — так нельзя (сломает старых клиентов).

## 🟢 Мягкие правила (хороший тон)

5. **Формат коммита:** `тип: короткое описание`. Типы: `fix:` (починка), `feat:` (новое), `refactor:` (переструктурирование без смены поведения), `docs:` (документация), `chore:` (мелочь/уборка).
6. **Маленькие частые коммиты.** Один коммит = одна понятная мысль. Легче читать, легче откатывать.
7. **Понятное сообщение.** Что и зачем, а не «фикс», «правки», «апдейт».

---

## Рабочий цикл (каждое изменение)

```bash
# 1. новая ветка под задачу (от dev)
git switch dev
git switch -c fix/понятное-имя

# 2. меняем маленькими шагами, коммитим по ходу
git add <файлы>
git commit -m "fix: что именно поправили"

# 3. перед слиянием — проверка COMPATIBILITY.md (не трогаю протокол?)

# 4. смотрим весь diff, потом merge в dev
git switch dev
git merge --no-ff fix/понятное-имя

# 5. push — ТОЛЬКО осознанно, после просмотра diff
git push origin dev
```

## Если что-то сломалось

```bash
git checkout baseline-2026-06   # вернуться к заведомо рабочему коду
```

---

## Ветки — что для чего

| Ветка | Назначение |
|-------|------------|
| `main` | стабильная, «как в поле». Не коммитить напрямую. |
| `dev` | интеграция готовых фич перед выпуском. Не коммитить напрямую. |
| `baseline-2026-06` | замороженный снимок рабочего состояния — точка возврата. Не трогать. |
| `fix/…`, `feat/…`, `refactor/…`, `docs/…` | рабочие ветки под конкретную задачу. Тут и живёт работа. |
