# Дизайн: параллельное воспроизведение Orange + ESP32 (режим file/scenario)

**Дата:** 2026-09-10
**Статус:** дизайн согласован (вариант А), готов к плану
**Репозитории:** клиент `sg_client_2026` + сервер `sg_orange_2026-` (обе части наши)
**Связанный воркстрим:** [[ksb-zone-4-channels-workstream]] (8 каналов/линий — основа)

## 1. Задача

Дать возможность воспроизводить звук **параллельно из двух источников** — Orange и ESP32 — и разделить это по вкладкам клиента:

- **Вкладка «Файлы»** (обычное воспроизведение): один источник — **Orange** играет на всех выбранных линиях (1..8).
- **Вкладка «Сценарии»**: два источника одновременно — **Orange** играет файл1 на линиях **1–4**, **ESP32** играет файл2 на линиях **5–8**.

**Вариант А (этот заход):** воспроизводится ровно **2 файла** (по одному на источник — Orange и ESP32). При этом UI сценариев делаем сразу на **8 combo-box** (сетка линий 1–8) с **автозаполнением по группам** — но пока с ограничением «один файл на группу» (см. §5.1). Полноценные 8 РАЗНЫХ файлов с оркестрацией 4 раундов — future (§8), но архитектурный задел под них оставляем (понадобится скоро).

## 2. Модель железа (контекст, уточнено sun0 2026-09-02)

- **Каналов 2 = ИСТОЧНИКА звука:** Orange и ESP32. Выбираются **коммутатором** (`Analog_in_commutator`): `orange_to_both_channel` (оба на Orange) / `orange_to_channel1_esp_to_channel2` (1-й на Orange, 2-й на ESP32).
- **Линий 8 = ДИНАМИКОВ:** `rel1..rel8` (сейчас вместо динамиков светодиоды). Галочка канала N → линия relN.
- «Канал» (источник, 2) ≠ «линия» (динамик, 8). В клиентском UI линии подписаны как «Канал 1..8».

## 3. Флаг режима

В команду `play` добавляется поле **`mode`**: `'file'` или `'scenario'`.
- Клиент выставляет его по активной вкладке (это уже решает `launch_play`: индекс вкладки → `orange_play` / `orange_play_scenario`).
- **Режим передаётся ВНУТРИ команды play** (самодостаточно), а НЕ как отдельное хранимое состояние вкладки на сервере — во избежание рассинхрона/гонок.
- **Совместимость флота:** если `mode` в команде отсутствует (старые клиенты, ~100 шт) → сервер трактует как `'file'` и ведёт себя как сейчас. Ключи протокола не переименовываем ([[ksb-fleet-compat-constraint]]).

## 4. Контракт двух файлов (вариант ii — реюз существующего ESP-пути)

В режиме `scenario` два файла доезжают до сервера **разными командами**, обе уже существуют:
- **Orange-файл** (линии 1–4): существующий поток `load` → `play` (теперь с `mode='scenario'`).
- **ESP-файл** (линии 5–8): существующие команды `load_esp` → `play_esp`.

Причина выбора: ESP-путь (`load_esp`/`play_esp`) на сервере **уже работает** (sun0 проверял звук ESP) — меньше нового протокола и риска.

## 5. Клиент — что меняется (`sg_client_2026`)

Хорошая новость: модель сценария **уже хранит два файла**:
- `ScenarioItemModel` содержит `file` (→ Orange, группа линий 1–4) и `file_esp` (→ ESP32, группа 5–8);
- UI сценариев (`ZoneLayoutManager`) уже сохраняет/загружает оба комбо-бокса.

Правки протокола/воспроизведения:
1. **`mode` в команду play** (`OrangeWorkerTCP`, там где формируется `{"command":'play', "filename":...}`) — добавить `"mode"`.
2. **Прокинуть mode из путей воспроизведения:** `orange_play` → `mode='file'`; `orange_play_scenario` → `mode='scenario'`.
3. **Досылать ESP-файл в сценарии:** `commit_orange_command_scenario` сейчас шлёт только Orange-файл; добавить отправку `file_esp` через `load_esp`/`play_esp` (когда `file_esp` непустой).

### 5.1 UI сценариев — 8 combo-box с автозаполнением по группам

- На каждую зону — **8 combo-box** (сетка линий 1–8), сгруппированы **1–4** (Orange) и **5–8** (ESP32). Расположение и подписи — по [[ksb-client-ui-design-rules]] (крупно, без эмодзи).
- **Автозаполнение по группе (Толкование 1):** выбор файла в любом combo-box группы 1–4 подставляет тот же файл во все 1–4; так же для 5–8. Ручное «переопределение» = сменить файл группы (через любой её combo-box).
- **Ограничение этого захода:** внутри группы всегда **один файл** (боксы группы связаны). Значит логически по-прежнему **2 файла** → хранятся в существующих `file` (группа 1–4) и `file_esp` (группа 5–8). Формат данных НЕ меняем.
- **Задел на future:** раскладку и обработчики писать так, чтобы переход к 8 независимым файлам (снять связку внутри группы + расширить модель на 8) был локальной правкой, а не переписыванием.
- Подписи групп сделать понятными: «Orange (линии 1–4)» / «ESP32 (линии 5–8)».

## 6. Сервер — что меняется (`sg_orange_2026-`)

1. **`play` читает `mode`** (`sg_main.py`, обработчик `data["command"]=="play"`) и прокидывает в `ServerState.play(...)`.
2. **`ServerState.play` ставит коммутатор по режиму** (инстанс `self.com` уже есть):
   - `mode='file'` → `self.com.orange_to_both_channel()`;
   - `mode='scenario'` → `self.com.orange_to_channel1_esp_to_channel2()`.
3. **Дефолт:** `mode` отсутствует → `'file'`.
4. ESP-воспроизведение идёт **не** внутри `play()`, а по существующему `play_esp` (контракт ii). `play()` отвечает за Orange-часть + коммутатор.

Разумно вынести выбор режима коммутатора в **чистую функцию-помощник** (напр. `resolve_source_mode(mode) -> 'both'|'split'`), чтобы покрыть юнит-тестом без железа.

## 7. Совместимость

- Старый клиент без `mode` → сервер трактует `'file'` → поведение как сейчас (регресса нет).
- Новые поля только добавляются; существующие ключи протокола/JSON не переименовываем.
- Клиентская модель сценария уже имеет `file_esp` — расширения формата не требуется.

## 8. Что НЕ входит в этот заход (future — понадобится скоро)

- **8 независимых файлов**: снять связку combo-box внутри группы (Толкование 2), чтобы в каждую из 8 линий можно было задать СВОЙ файл.
- **Оркестрация 4 раундов**: играть парами по 2 параллельно за 4 последовательных раунда (раунд N: файл линии N на Orange ‖ файл линии N+4 на ESP32).
- Расширение модели/формата сценария с 2 файлов до 8 (по одному на линию).
- **Задел:** UI на 8 combo-box (§5.1) и серверную часть пишем так, чтобы этот переход был локальной правкой (снять связку в группе + цикл раундов на сервере), не переписыванием базы.

## 9. Проверка

- **unittest (без железа):** выбор коммутатора по `mode` (чистая функция, вкл. дефолт при отсутствии `mode`); клиентское формирование команды `play` с `mode`; отправка `file_esp` в сценарии при непустом значении.
- **Железо (ОТЛОЖЕНО):** реальный параллельный звук — Orange на 1–4 и ESP32 на 5–8 одновременно; переключение коммутатора; отсутствие конфликтов на `/dev/ttyS1`. Проверяется на физическом Orange (когда появится у владельца) или прогоном sun0. Не блокер для написания кода ([[ksb-server-analysis-only]]).
